# 재무 비율의 서로 다른 기록 통화 차단

2026-11-15. MD §17/SDD04·05의 통화·단위·비교 가능성 요구에 따른 AI 내부 보수 경계다. 통화가 다른 계정 금액을 환산 없이 나눠 정상 %로 표시하는 문제를 합성 회귀로 확인했다.

## 정확한 범위

같은 연도의 다음5개 비율만 대상으로 한다.
- ROE: 당기순이익/자본총계
- 영업이익률: 영업이익/매출
- 순이익률: 당기순이익/매출
- 부채비율: 부채/자본
- 유동비율: 유동자산/유동부채

두 계정이 존재하고 기록된 currency가 다르면 기존 value=null/status=unavailable 및 사유로 반환한다. 원천금액이 없다는 MISSING 대신 CURRENCY_MISMATCH_<METRIC> risk flag로 구분하고, 계산하지 않은 비율 evidence는 생성하지 않는다. 나머지 독립된 정상 비율·같은 통화의 비율은 보존하며 환율이나 환산 금액을 만들지 않는다. 요청/응답 schema·필드 추가·Backend/Frontend 수정은 없다. unavailable 값은 기존 점수 계산에서 제외된다.

## 직접 검사

`test_ratio_currency.py`의4개 회귀는5비율의USD/KRW 불일치, 같은KRW/USD의 정상·0·음수, 독립 정상 비율 보존 및 기존 계정 결측 사유를 확인한다. 수정 전2개 실패(35/37), 수정 후 계산/정규화/골든 합계37/37 통과했다. 직접 재현 명령:

```powershell
# Python3.12, lock Pydantic2.13.4 및 전이 의존성의 별도 환경
python -I ai/tests/fundamental/test_calculators_isolated.py
```

같은 보호 runner의 설정literal/순수ShareCountData만 로드, 외부IO/비밀/파일쓰기 차단은 유지한다. 실제 graph·공급자·DB·환산·서비스 통합 검증이 아니다.

## 남은 경계

MetricValue.currency에는 기존 KRW fallback이 있다. 이번 변경은 기록 문자열이 다른 비율을 보수적으로 막을 뿐, 원천 통화가 누락됐다는 provenance를 비율 전체에 새로 도입하거나 같은KRW 표기가 실제 같은통화임을 인증하지 않는다. 누락통화 전체 해결·단위검증·실제공시통화/기간정확성 완료를 주장하지 않는다. 연도간 비교와 명시적 비KRW 표시의 후속 보수 차단은 아래에 구분한다. 그런 확대는 별도 설계·근거가 필요하다. Backend·공용계약·프론트·PR61·운영·유료호출·git게시 변경은 없다.


## 후속: 연도간 성장·추세 우회 및 비KRW 원화 오표시

매출성장률·영업이익성장률은 해당 지표의 당기/전기 기록통화가 다르면 같은 기존 unavailable/사유/통화flag로 차단한다. 퍼센트뿐 아니라 서로 다른 통화의 원금액으로 흑적자전환·저기저회복을 단정하지 않도록 direction/display도 제거한다. 같은통화의 정상%는 유지한다.

기존 build_trend는 금액에 통화 필드가 없고 formatter/HTML/payload가 원화표시를 고정하므로, 다중통화금액series는 같은 연도축/길이를 유지한 null로 마스킹한다. ROE는 같은연도의 분자/분모통화가 다른 지점만 null로 둔다. 나머지 독립series와 유효ROE는 보존한다. calc_node는 기존 risk_flags에 TREND_CURRENCY_MISMATCH_<METRIC>를 전달한다. schema 필드추가는 없다.

사용자 지시로 명시적 비KRW의 단일연도 오표시도 차단했다. 정확한 다통화표시를 새로 설계하는 대신 기존 원화계약에서 제공할 수 없는 값은 불가처리한다. 명시적 비KRW 금액trend는 단일연도도null+TREND_UNIT_UNSUPPORTED이며, 비KRW EPS/BPS는 기존unavailable+원화표시불가사유/CURRENCY_UNIT_UNSUPPORTED와근거없음으로 반환한다. KRW 단일연도의0/음수와연도축, 같은통화의%비율은 유지한다. AI HTML에는 해당flag의 읽을수있는 단위/환산불가설명만 추가했다.

최초 연도간/추세회귀는3개 제품assertion실패와1개 LangGraph 미설치 수집실패를 보였다(38/42). node 검사는 unsafe package import 대신 실제함수 AST 및 실제순수의존성을 조립하도록 바꿨다. 최종 계산/정규화/골든/통화회귀 및 기존formatter5/schema1/HTML12와 비KRW 전체HTML회귀까지 **66/66** 통과했다. 기존payload의null금액은 false available원화행으로 export되지 않고, 실제format/HTML에서 산출불가가됨을 확인했다. 전체Pydantic응답schema의새필드는없다.

누락통화의KRW기본값 진위와 원천provenance 전체·공시단위/기간정확성·실제외부자료·Backend저장왕복·브라우저 수용은 여전히 미검증이다. null마스킹은 보수 차단이며 환산이나 완전한 다통화지원이 아니다. HTML builder는 기존1025줄→현재1035줄의초과파일이며 이번에는flag설명구문만작게추가했다. 임의분할은하지않았다. 신규코드/테스트파일은400줄내외다. Backend/Frontend/PR61/유료/운영/git게시변경은없다.

저기저의 절대 임계값을 비KRW 자료에 어떻게 적용할지와 원천통화 누락의 전체 provenance는 여전히 별도 정책/설계가 필요하다. 같은 기록통화가 있다는 사실만으로 모든 금융 비교 가능성을 인증하지 않는다.


### P2 리뷰 후속: 저기저 금액 임계값의 통화 호환

독립 리뷰가 지적한 USD 영업이익·KRW 매출의 저기저 오분류도 보완했다. 같은 지표의 연도간 통화가 같아 정상 성장률을 구할 수 있어도, 매출과 영업이익의 통화가 다르면 매출비례 저기저 금액 임계값은 적용하지 않는다. 양수 매출이 없어 절대 임계값을 써야 하는 경우에는 기록통화가 원화일 때만 사용한다. 비KRW·통화호환 미확인 경로에서는 그 금액 임계값 분기만 건너뛰고 정상 성장률을 유지한다. 기존 무차원 300% 극단성장 표시정책과 같은통화 양수매출의 비례기준/원화 절대기준은 보존한다.

추가4개 중2개가 수정 전 실패(68/70), 수정 후 전체70/70 통과했다. 서로 다른 통화의 매출, 비KRW 매출없음/0/음수, 정상80% 및 근거, 호환 상대·원화 절대 임계값과 기존 극단성장정책 유지가 포함된다. 원천통화 누락의KRW fallback provenance를 입증한 것은 아니며, 환산/새 임계값을 만들지 않았다. 기존 정책값과 공용schema는 그대로다.

원문통화누락의 새실행경로 후속 및 실제반환경로 검증은 [내부provenance분리](fundamental-currency-provenance.md)에 기록한다. 이전 누락provenance 미해결 문장은 해당회차 이력이며, 구형결과의 소급증명·실제통화진위 검증 한계는 계속 남는다.
