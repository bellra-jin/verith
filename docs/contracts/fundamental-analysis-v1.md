GET `/{analysis_id}` does not dispatch or publish; expiry bookkeeping may be committed. Server fixes request timestamp once; no public as_of or owner. Registered stock required. Default off.

The fixed Flow/Fundamental profiles use one coordinator. It commits claim before HTTP, validates/freezes original canonical JSON before publication, then stages root/children/index + stored in one transaction. Unknown commit never redispatches. A result_ready GET only observes; an explicit same-key POST can publish the preserved snapshot without another AI call. Consent/session/CSRF/Origin still apply. Same key/input reuses identity; changed input conflicts. Only exact report uniqueness is a conclusive collision. Deleted ledger retains IDs/hashes and clears request/input/result text.

Nested original engine request has exactly request_id/trace_id/ticker/query. Request context schema `fundamental.request-context.v1` is not financial source data. Deadline 60s, Backend HTTP total65s, BFF total70s; no retry. One worker slot remains held until actual worker/default-executor completion after timeout/cancellation. This is per process and does not prove provider cancellation or billing stops.

Reads compare snapshot against all projections; no legacy fallback. Stage has no transaction control. Delete locks session -> run -> original root, then tombstones/scrubs/deletes atomically; shared stock stays.

UI uses separate account/tab pending identity, explicit POST and GET-only refresh/recovery, private BFF, structured text, and http/https source links only. No public raw save, bulk deletion, iframe/HTML/PDF rendering. Missing periods stay unknown; current request time never substitutes for source financial dates. ## CF060 mandatory admission counts

New native runs require both `FUNDAMENTAL_USER_DAILY_REQUEST_LIMIT` and `FUNDAMENTAL_SERVICE_DAILY_REQUEST_LIMIT`. Missing/invalid settings close only new admission with `FEATURE_UNAVAILABLE`; there is no numerical default or new activation flag. Values are explicit positive integers or canonical positive decimal strings in `1..2^63-1`; booleans, fractions, whitespace/sign/zero/overflow are rejected. A user's cap may exceed the service cap, which remains independently enforced.

The existing coordinator always receives a Fundamental count-only control. Only a missing owner/key parses one immutable policy; only the winning INSERT reserves a count on the same session/transaction. READ COMMITTED is checked on that connection, then the operation-wide fixed `pg_try_advisory_xact_lock(0x466E644C696D6974)` must succeed. A separate subsequent COUNT sees the KST day `[midnight, next midnight)` containing the DB `started_at`, including the current INSERT and every existing run state/legacy run. `count == limit` is allowed; exceeding either limit returns `USAGE_LIMIT_EXCEEDED` and rolls back admission. Busy/unknown isolation fails closed with `SERVICE_UNAVAILABLE`, without lock retry/fallback. Contention can temporarily refuse an otherwise eligible request.

Commit ACK remains required before dispatch and releases the transaction lock before awaiting the AI client. ACK loss, timeout, cancellation, unknown/failed runs and deleted tombstones never refund a committed count or grant another dispatch. Same-key observation, permitted result_ready publication recovery and GET do not parse/consume new limits. Existing feature/auth/CSRF/owner gates remain: this does not open GET when the existing overall feature gate is disabled. Injecting the existing control changes new unregistered-stock/empty-name eligibility from `INPUT_INVALID` to `FEATURE_UNAVAILABLE`; other profiles and the coordinator are unchanged.

There is no new table/model/migration/counter ledger or use of Flow's monetary ledger. `observe` is an explicit no-op, with no provider-usage, refund, zero-cost assertion or settlement ACK. All workers must have the same explicit policy before activation; without a durable policy snapshot, the DB does not prove worker configuration equality. Changed policies/new service instances still count all existing runs and do not reset history.

This limits committed admissions, not internal model calls/tokens, request rate or money. Supervisor Fundamental execution remains unconnected. Before that work, the AI owner must provide an applied interpretation or explicit rejection bound to the original typed conditions, enforceable provider/fallback/regeneration/input/output/deadline/cost limits and usage/unknown evidence. Existing raw query and financial source semantics are preserved. No provider call or production activation is part of CF060.

## CF061 public request deadlines

The Fundamental access boundary fixes ingress monotonic time T once. POST analyses body receipt and strict input validation share T+15 seconds, including all chunks. Before extending its accumulator it requires a bytes chunk and checks `len(chunk) <= 4096 - len(raw)`; an oversized or invalid chunk remains INPUT_INVALID/422 without downstream authentication/DB/analysis. This bounds the middleware's additional copy, not the ASGI server's original allocation.

Body, auth/session/DB dependencies, downstream handling and normal response sends share T+65 seconds for POST, GET and DELETE. Own timeout before any response-start attempt produces the existing SERVICE_UNAVAILABLE/503. Body-timeout error delivery stays within T+65; only total-timeout response delivery may use the original T+70 response-only window after cleanup. That window never restarts analysis, authentication or database work. If cleanup passes T+70, no new response starts.

Only an expired owned timeout context or the boundary's explicit monotonic fence is translated. Internal TimeoutError, external CancelledError and disconnect propagate. A response-start attempt is irreversible even when send fails; timeout, partial response or send failure cannot trigger a second response. Request IDs and private/no-store, Vary: Cookie, Origin remain unchanged.

These are cooperative cancellation boundaries, not hard completion guarantees. Blocking synchronous code or slow dependency cleanup can exceed the timestamps; physical AI/provider termination and billing cessation are not guaranteed. Native run60/AI HTTP65/BFF70, retry0, claim/commit ACK, count-only admission, unknown/hold, same-key recovery and owner checks are unchanged. The middleware does not rewrite runs, refund counts or grant retries. Synthetic ASGI cleanup tests do not constitute PostgreSQL/provider/production acceptance.

## Fundamental usage completeness classification

`fundamental/domain/usage_evidence.py` is a pure, internal contract using existing `AnalysisContext`, strict finite JSON and canonical/hash helpers. It does not use Flow's fixed prices/slots/partial release or claim that Flow's non-anomalous check proves ALL-known usage. No provider/model/price/call/cost policy values are installed. Current Fundamental `cost_summary` can sum only non-missing token entries; `llm_calls`, aggregate subtotals and producer `complete` flags never establish a complete call inventory.

A backend-owned immutable `UsageExpectation` binds the Fundamental operation, owner/run/admission/attempt/input/time context, explicit policy digest, canonical call inventory and `inventory_closed`. Every call fixes a nonzero canonical UUID, provider, model, service tier, canonical request digest and explicit input/output caps. The inventory must enumerate all potentially billable attempts, including fallback, retries and failed/uncertain sends. A planned maximum is insufficient; absent/unclosed/empty inventory remains `unknown`. Hashes bind bytes and are not provider authentication or owner authorization.

An evidence document has exactly `schema_version: fundamental.usage-evidence.v1`, `expectation_sha256` and `calls`. Each call contains the expected identity/provider/model/tier/request digest and exact `input_tokens`, `cached_tokens`, `output_tokens`, `total_tokens`. Unknown token values remain null. Known tokens must be true nonnegative int64 integers (not bool/float/string), cached<=input, input+output=total and within the caller's caps. Default `usage_trusted=False` stays unknown; only an independently verified caller-side collector may vouch for receipt provenance. Copying an AI `complete` or trust flag into these caller arguments is forbidden.

`classify_usage` accepts the entire retained receipt tuple. Only an authoritative nonempty closed inventory, independently trusted receipts, exact identity/policy binding and known consistent usage for every call yield `complete_usage`. Missing calls/tokens/receipts, aggregate-only data or absent provenance yield `unknown`; invalid shapes/types/ranges, cross-binding, unexpected calls, cap violations or conflicting duplicate evidence are `rejected`. Canonical identical repeats and input order do not change the assessment or totals; conflicting values for one ID are retained together and never overwritten. Totals are absent for unknown/rejected or aggregate overflow, rather than being a misleading partial sum. The document/set parsing bound is64KiB, a memory/validation boundary rather than a financial limit; collection separators/brackets and null receipts consume the same budget, with a pre-traversal collection-length bound. Inputs exceeding it are rejected.

All assessments keep `keep_reservation=True`, including `complete_usage`. This means complete token evidence is a prerequisite for a future independently authorized pricing/settlement path, not an amount, invoice, refund or settlement ACK. This unit creates no reservation/receipt ledger, schema, operational flag, durable idempotency or execution right. A future integration must persist all evidence/conflicts, verify policy/price/source completeness and perform an atomic idempotent settlement on the matching reservation. It must not drop a rejected receipt on a later replay. Existing Fundamental observe remains count-only/no-op; adapter/public DTO/stored raw output and other operations' accounting are unchanged. Current Fundamental has no monetary reservation mechanism; this contract does not pretend to add one, and previously preserved reservations are untouched.

AI-owner handoff: supply request-bound per-call identities and complete independently verifiable call inventory, model/tier and request digests, all token components including cached/total, fallback/retry/failed-send evidence, explicit enforced call/token/cost policy and unknown handling. Until that producer/collector contract and safe Backend reservation/settlement integration exist, actual billing control and Supervisor Fundamental execution remain closed. No direct contact or AI/frontend modifications are part of this unit.
